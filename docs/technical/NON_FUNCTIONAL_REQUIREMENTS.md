# 非功能需求

版本：1.0  
状态：V1.0 基线

## 可用性与恢复

- 任务状态必须持久化；刷新、前端关闭和服务重启后从最后成功检查点恢复。
- 同一 operation_key 不得重复执行。
- 所有重试有限，超限进入明确失败或人工处理状态。
- V1.0 目标 RPO 为最近一次成功检查点，RTO 在真实基准建立后量化；未测量前不得承诺数值。

## 性能与容量

- 普通 UI 操作不得被模型或媒体长任务阻塞。
- 列表和历史接口必须分页；媒体二进制不得写入 JSON 状态文件。
- 每项长任务声明超时、并发上限、最大输入、最大输出和磁盘预算。
- 性能门槛以基准测试结果写回，不使用未经测试的固定承诺。

## 安全与隔离

- 每次访问校验 tenant_id、user_id、project_id、session_id 和 scope。
- 密钥不进入代码、日志、文档和前端。
- 外部服务默认关闭；启用时只发送最小必要数据。

## 可维护性

- 契约、状态机、迁移和插件接口必须有自动测试。
- 新代码不得增加第二套目录、命名、请求、状态或配置实现。
- 错误必须包含 request_id/trace_id 和可操作的用户说明。

## 可观测性

- 日志、指标快照、trace和告警必须通过统一可插拔exporter输出；单机V1至少提供可持久JSONL和可原子抓取的Prometheus textfile，多主机不得依赖共享本地文件。
- 可观测记录不得包含密钥或授权字段；结构化嵌套字段同样执行秘密检测。Prometheus标签必须有界，request_id、trace_id、task_id等高基数字段进入日志和span。
- 告警证据至少包含规则、实际值、阈值、时间和适用的request_id/trace_id，并能按运行手册执行隔离演练。
- 队列年龄、API延迟、取消时延、worker失联、租约丢失及磁盘余量阈值由真实容量基准写回；未实测前不得宣称生产SLA。
